# 성능 예산

## 문서 역할

성능 예산은 "어느 정도까지 허용할 것인가"를 미리 정하는 문서입니다.  
Paper 서버는 TPS가 중요하므로, 반복 작업과 엔티티 수에 상한을 둡니다.

## 기본 목표

- 목표 TPS: 20 TPS
- 필수 플레이어: 4명 이상
- 참가 인원: 짝수만 허용
- 최대 플레이어: 10명
- 팀 크기: 2명
- 게임 중 메인 스레드 작업 최소화
- 매 tick 전체 갱신 금지
- Display 엔티티와 드롭 아이템 수 제한

## Mayuela 성능 예산표

| 항목 | 기본 예산 | 이유 |
| --- | ---: | --- |
| 최대 플레이어 | 10명 | 기획상 제한 |
| 최소 플레이어 | 4명 | 2vs2 최소 성립 |
| 팀 크기 | 2명 | 2vs2vs2vs2vs2 구조 |
| 권장 최대 제단 수 | 20개 | 점령/표시 갱신 비용 제한 |
| 머리 위 `ItemDisplay` | 최대 10개 | 플레이어당 1개 |
| 제단 위 `TextDisplay` | 최대 제단 수만큼 | 점령 제단 표시 |
| 제단 발광 대상 | 최대 제단 수만큼 | 점령 상태 표시 |
| 코인 필드 아이템 | 기본 최대 40개 | 아이템 엔티티 누적 방지 |
| 활성화율 계산 주기 | 20 tick | 1초 단위 계산 |
| 제단 1개당 기본 증가량 | 0.08~0.2% | 목표 경기 시간에 따라 조정, 기본 운영 권장값은 0.08% |
| 코인 드롭 주기 | 인원별 설정 | 4/6/8/10명 인플레이션 제어 |
| 스코어보드 갱신 | 변경 시 우선 | 전체 갱신 방지 |
| lore 갱신 | 변경 시 우선 | 불필요한 ItemMeta 생성 방지 |
| YAML 저장 | 명령어/시작/종료 시점 | 게임 중 IO 반복 방지 |

## Scheduler별 예산

| Task | 주기 | 최대 처리량 |
| --- | ---: | --- |
| `ActivationTickTask` | 20 tick | 플레이어 10명, 제단 20개 |
| `PlayerDisplayFollowTask` | 1~2 tick | 플레이어 10명 |
| `CoinDropTask` | 인원별 설정 | 코인 최대 40개 이하일 때만 드롭 |
| `DroppedCoinCleanupTask` | 100~200 tick | Mayuela 코인만 정리 |
| `ScoreboardUpdateTask` | 변경 시 | 변경된 플레이어만 |
| `AltarDisplayUpdateTask` | 변경 시 | 변경된 제단만 |

## 금지 패턴

다음 코드는 성능 예산 위반으로 봅니다.

- 매 tick YAML 저장
- 매 tick 모든 플레이어 스코어보드 전체 재생성
- 매 tick 모든 제단 TextDisplay 재생성
- 매 tick 월드 전체 블록 탐색
- 매 tick 주변 엔티티 넓은 범위 검색
- 코인 아이템 개수 제한 없이 계속 드롭
- Display 엔티티를 update 대신 remove/spawn 반복

## 성능 판단 기준

1인 개발에서는 복잡한 벤치마크보다 아래 질문으로 판단합니다.

- 이 작업은 매 tick 실행되어야 하는가?
- 값이 바뀌지 않았는데 갱신하고 있지 않은가?
- 한 번 찾아둔 위치를 다시 월드에서 검색하고 있지 않은가?
- 엔티티를 재사용할 수 있는데 새로 만들고 있지 않은가?
- 파일 저장이 게임 진행 중 반복되고 있지 않은가?

## 성능 로그 권장

개발 중에는 다음 로그를 디버그 모드에서 확인할 수 있게 합니다.

- 현재 참가자 수
- 등록 제단 수
- 현재 Display 엔티티 수
- 필드 코인 아이템 수
- 실행 중인 scheduler task 목록
- 활성화율 tick 처리 시간

## 예산 초과 시 대응

| 문제 | 대응 |
| --- | --- |
| 코인 아이템이 너무 많음 | 드롭 중지 또는 오래된 코인 제거 |
| Display 엔티티가 누적됨 | 게임 종료/퇴장 시 제거 로직 점검 |
| 스코어보드 갱신이 많음 | 변경 감지 방식으로 전환 |
| 활성화율 계산이 무거움 | 제단 상태 캐시 사용 |
| YAML 저장이 잦음 | 저장 시점 조정 |
