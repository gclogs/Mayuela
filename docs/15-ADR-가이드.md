# ADR 가이드

## 문서 역할

ADR은 Architecture Decision Record의 약자입니다.  
개발 중 중요한 기술 결정을 왜 그렇게 했는지 기록하는 짧은 문서입니다.

1인 개발에서는 ADR을 거창하게 작성할 필요가 없습니다.  
나중에 코드를 다시 볼 때 "왜 이 구조로 만들었지?"를 빠르게 이해할 수 있으면 충분합니다.

## ADR이 필요한 순간

다음 중 하나라도 해당하면 ADR을 작성합니다.

- 되돌리기 어려운 구조 결정을 할 때
- 성능에 큰 영향을 줄 수 있는 결정을 할 때
- Paper API, ItemsAdder, YAML 같은 외부 의존성을 선택할 때
- 파일명, 데이터 구조, 저장 방식처럼 이후 구현 전체에 영향을 주는 결정을 할 때
- 두 가지 이상의 선택지가 있고 장단점이 분명할 때

## Mayuela에서 ADR이 필요한 결정 예시

| 결정 주제 | 기록이 필요한 이유 |
| --- | --- |
| Paper `1.21.11` 기준 사용 | API와 서버 버전 기준 고정 |
| `alter.yml` 유지 또는 `altar.yml` 교정 | 파일명 오타 가능성과 호환성 문제 |
| 색깔 블록을 핫바 9번에 고정 | UX와 이벤트 차단 정책에 영향 |
| 제단 활성화율을 누적형으로 계산 | 승리 조건과 밸런스에 영향 |
| Display 엔티티를 재사용 | TPS 퍼포먼스에 영향 |
| YAML 저장 시점 제한 | 데이터 안정성과 성능에 영향 |
| Folia 지원 여부 | scheduler 설계에 영향 |

## ADR 작성 형식

ADR은 아래 형식으로 작성합니다.

```md
# ADR-번호 제목

## 상태

제안됨 / 승인됨 / 변경됨 / 폐기됨

## 배경

왜 이 결정을 해야 하는지 설명합니다.

## 선택지

- A안:
- B안:
- C안:

## 결정

선택한 방식을 적습니다.

## 이유

왜 이 방식을 선택했는지 적습니다.

## 결과

이 결정으로 생기는 장점, 단점, 주의점을 적습니다.
```

## ADR 예시

```md
# ADR-001 Paper 1.21.11 기준 사용

## 상태

승인됨

## 배경

Mayuela는 `ItemDisplay`, `TextDisplay`, Adventure HEX 색상, Paper scheduler를 사용합니다.
기획 문서도 1.21.11 기준으로 작성되어 있습니다.

## 선택지

- A안: 1.21 기준으로 개발
- B안: 1.21.11 기준으로 개발

## 결정

Paper 1.21.11 기준으로 개발합니다.

## 이유

문서, API, 테스트 서버 버전을 일치시키면 구현 중 API 차이로 인한 혼란을 줄일 수 있습니다.

## 결과

`build.gradle`의 compileOnly와 runServer 버전을 같은 기준으로 맞춰야 합니다.
```

## 1인 개발용 ADR 운영 규칙

- ADR 하나는 1~2분 안에 읽을 수 있게 짧게 작성합니다.
- 모든 고민을 ADR로 만들지 않습니다.
- 코드 구조, 데이터 구조, 성능, 외부 의존성 결정만 기록합니다.
- 결정이 바뀌면 기존 ADR을 지우지 않고 `변경됨`으로 표시한 뒤 새 ADR을 추가합니다.

## 권장 폴더

ADR 문서는 다음 폴더에 저장합니다.

```text
docs/adr/
```

예시:

```text
docs/adr/ADR-001-paper-1-21-11.md
docs/adr/ADR-002-alter-yml-name.md
docs/adr/ADR-003-display-entity-reuse.md
```
