# 개발 원칙

## 문서 역할

Mayuela를 Paper 서버 기반으로 개발할 때 반드시 지켜야 하는 엔지니어링 원칙을 정의합니다.  
이 문서는 코드 구조와 서버 퍼포먼스 판단 기준으로 사용합니다.

## 핵심 원칙

Mayuela 개발에서 가장 중요하게 보는 기준은 다음 두 가지입니다.

1. SOLID 원칙을 지켜 기능별 책임을 명확히 분리합니다.
2. 마인크래프트 3D 게임 서버 특성상 TPS 퍼포먼스를 최우선으로 고려합니다.

## 1. SOLID 원칙

Mayuela는 게임 세션, 제단, 활성화율, 스코어보드, 디스플레이 엔티티, 아이템, 상점, YAML 저장, 이벤트 처리가 함께 동작하는 플러그인입니다.  
따라서 하나의 클래스가 여러 시스템을 동시에 책임지면 유지보수가 빠르게 어려워집니다.

### 권장 책임 분리

| 책임 | 예시 클래스 |
| --- | --- |
| 게임 상태 전환 | `GameSessionManager` |
| 플레이어 입장, 퇴장 관리 | `GamePlayerService` |
| 팀 색상 수동/랜덤 배정 | `TeamService` |
| 제단 점령 및 활성화율 계산 | `AltarService` |
| 스코어보드 표시 | `ScoreboardService` |
| `ItemDisplay`, `TextDisplay` 관리 | `DisplayService` |
| 색깔 블록 이동 차단 | `ItemLockListener` |
| 상점과 코인 처리 | `ShopService`, `CoinService` |
| YAML 로드 및 저장 | `ConfigRepository` |

### 설계 기준

- 하나의 클래스는 하나의 명확한 책임만 가집니다.
- 이벤트 리스너는 이벤트를 직접 처리하되, 복잡한 비즈니스 로직은 서비스로 위임합니다.
- YAML 파일 접근은 저장소 계층으로 모읍니다.
- UI 갱신 로직은 게임 규칙 계산 로직과 분리합니다.
- Paper API 의존이 강한 코드는 도메인 계산 코드와 분리합니다.
- 기능 추가 시 기존 클래스를 거대하게 키우기보다 적절한 서비스나 정책 객체로 분리합니다.

## 2. TPS 퍼포먼스 원칙

Paper 서버는 기본적으로 20 TPS를 목표로 동작합니다.  
메인 스레드에서 무거운 작업을 수행하면 서버 전체 렉으로 이어지므로, 모든 시스템은 TPS 비용을 고려해 설계합니다.

### 주의해야 할 작업

- 매 tick 모든 플레이어와 모든 제단을 무조건 순회하는 작업
- `ItemDisplay`, `TextDisplay`를 불필요하게 자주 teleport 또는 재생성하는 작업
- 스코어보드, lore, TextDisplay를 매 tick 전체 갱신하는 작업
- 게임 도중 YAML 파일을 반복적으로 읽고 쓰는 작업
- 월드 전체 블록 탐색 또는 넓은 범위 엔티티 검색
- 불필요한 객체를 tick마다 대량 생성하는 작업
- 비동기 스레드에서 Bukkit/Paper API를 직접 호출하는 작업

### 퍼포먼스 기준

- 스코어보드, lore, TextDisplay는 값이 변경되었을 때만 갱신합니다.
- 제단 활성화율 계산은 설정된 주기마다 실행하고, 필요 없는 tick 작업을 만들지 않습니다.
- 표시 엔티티는 재생성보다 재사용을 우선합니다.
- YAML 저장은 명령어 실행, 게임 시작, 게임 종료, 서버 종료 같은 명확한 시점에만 수행합니다.
- 월드 스캔 대신 등록된 좌표와 캐시된 상태를 사용합니다.
- Bukkit/Paper API 호출은 기본적으로 메인 스레드에서 수행합니다.
- 파일 IO, 무거운 직렬화, 통계 계산은 가능하면 비동기로 분리하되, 결과 적용은 메인 스레드에서 수행합니다.

## Mayuela 시스템별 퍼포먼스 지침

| 시스템 | 지침 |
| --- | --- |
| 제단 활성화율 | 모든 tick이 아니라 설정 주기마다 누적 계산 |
| 스코어보드 | 표시 값이 바뀐 플레이어만 갱신 |
| 색깔 블록 lore | 활성화율, 제단 수, 증가량 변경 시 갱신 |
| 머리 위 `ItemDisplay` | 최대 10명 기준으로 관리하되, 불필요한 재생성 금지 |
| 제단 위 `TextDisplay` | 점령자 또는 퍼센트 변경 시 갱신 |
| 발광 효과 | 점령자 변경 시에만 색상 갱신 |
| 코인 드롭 | 드롭 주기와 최대 필드 아이템 수 제한 |
| YAML 저장 | 게임 중 반복 저장 금지, 상태 변경 지점 중심 저장 |

## 코드 리뷰 기준

개발된 코드는 다음 질문을 기준으로 리뷰합니다.

- 이 클래스의 책임이 하나로 설명되는가?
- 이벤트 리스너가 너무 많은 게임 규칙을 직접 처리하고 있지 않은가?
- 매 tick 실행되는 코드가 꼭 필요한가?
- 값이 바뀌지 않았는데 UI를 다시 갱신하고 있지 않은가?
- 게임 중 파일 IO가 반복되고 있지 않은가?
- 표시 엔티티를 필요 이상으로 생성하거나 제거하고 있지 않은가?
- Bukkit/Paper API를 비동기 스레드에서 직접 호출하고 있지 않은가?
