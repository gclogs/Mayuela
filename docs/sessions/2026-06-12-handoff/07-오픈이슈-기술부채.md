# 오픈 이슈와 기술부채

이 문서는 현재 세션 기준으로 남아 있는 위험, 기술부채, 후속 작업을 우선순위로 정리합니다.

## 우선순위 기준

- `P0`: 즉시 수정 필요. 게임 진행 불가 또는 데이터/아이템 손상 가능.
- `P1`: 다음 개발 사이클에서 우선 수정. 밸런스/운영/유지보수에 큰 영향.
- `P2`: 계획적으로 정리. 기능 확장 전 해두면 좋음.
- `P3`: 여유 있을 때 정리.

## P1. 현상수배 old 코드 제거

문제:

- `AltarService`에 과거 제단 3개 기준 현상수배 메서드 흔적이 남아 있습니다.
- 현재 호출 경로는 `refreshBountyStatus(long elapsedSeconds)`입니다.
- no-arg `refreshBountyStatus()`는 죽은 코드지만, 남아 있으면 오해와 회귀를 유발합니다.

권장 작업:

- no-arg `refreshBountyStatus()` 완전 제거
- 깨진 한글 문자열 정리
- 현상수배 판정을 `BountyService`로 분리 검토

완료 기준:

- `rg -n "refreshBountyStatus\\(" src/main/java` 결과가 `long elapsedSeconds` 버전 호출만 보여야 합니다.
- `rg -n "BOUNTY_ALTAR_THRESHOLD" src/main/java` 결과가 없어야 합니다.

## P1. 현상수배 통계 이벤트 추가

문제:

- 현상수배 발동/해제/보상 지급이 별도 이벤트로 충분히 기록되지 않습니다.
- 현재는 사망 이벤트와 설정값으로 간접 추론해야 합니다.

권장 이벤트:

- `BOUNTY_ACTIVATED`
- `BOUNTY_RELEASED`
- `BOUNTY_REWARD_GRANTED`
- `BOUNTY_REWARD_ALREADY_CLAIMED`
- `BOUNTY_REWARD_FAILED`

데이터:

- leader-team-id
- runner-up-team-id
- lead-gap
- reward-coins
- killer
- victim
- reason

완료 기준:

- 통계 파일만 보고 현상수배가 승패에 미친 영향을 분석할 수 있어야 합니다.

## P1. 코인 통계 의미 분리

문제:

- `GamePlayer.coins`가 누적 획득량인지 현재 보유량인지 모호합니다.
- 상점 구매 시 실제 인벤토리 코인은 줄어들지만 `GamePlayer.coins`가 소비량과 분리되어 있지 않습니다.

권장 모델:

```text
earnedCoins
spentCoins
finalHeldCoins
fieldPickupCount
bountyRewardCoins
```

완료 기준:

- 매치 종료 통계에서 팀별 “총 획득”, “총 소비”, “최종 보유”가 분리되어야 합니다.

## P1. 인코딩 깨짐 정리

문제:

- README, Java 메시지, 일부 문서에 깨진 한글이 있습니다.
- 패치와 리뷰가 어려워집니다.
- 실제 서버 메시지 품질이 낮아집니다.

권장 작업:

- UTF-8 기준으로 문자열 정리
- 명령어 label/plugin.yml도 함께 확인
- 메시지 문자열을 별도 `Messages` 클래스로 모으는 방안 검토

주의:

- 로직 변경과 문자열 정리를 같은 PR에 섞지 않는 것이 좋습니다.

## P1. DisplayEntity 누락 정리 검증

문제:

- 플레이어 ItemDisplay, 현상수배 TextDisplay, 제단 TextDisplay, 코인 TextDisplay가 모두 존재합니다.
- 제거 누락 시 월드에 엔티티가 남을 수 있습니다.

권장 작업:

- `/game 모니터링`에 Mayuela DisplayEntity 추정 수 추가
- 게임 종료 후 DisplayEntity 제거 확인 로그 추가
- 코인 TextDisplay와 Item 엔티티의 생명주기 묶음 테스트

완료 기준:

- 게임 종료 후 Mayuela가 생성한 DisplayEntity가 남지 않아야 합니다.

## P2. ItemsAdder 연동 공통화

문제:

- `InventoryService`, `ShopService`, `CoinService`가 ItemsAdder reflection 코드를 각각 가지고 있습니다.

권장 작업:

- `ConfiguredItemFactory`
- `ItemsAdderBridge`
- `ModelItemService`

중 하나로 공통화합니다.

공통화 범위:

- ItemsAdder id로 ItemStack 생성
- fallback material 적용
- amount 설정
- 실패 시 null 또는 fallback 반환 정책

완료 기준:

- ItemsAdder reflection 코드는 한 클래스에만 존재해야 합니다.

## P2. 현상수배 해제/쿨다운 UX 검증

문제:

- 현상수배는 발동 10%, 해제 7%, 쿨다운 30초입니다.
- 실제 플레이에서 해제가 너무 늦거나 너무 빠르게 느껴질 수 있습니다.

검증 방법:

- 테스트용으로 `warmup-seconds`를 낮춰 4명 팀전 테스트
- 1등과 2등 격차를 10% 이상 벌림
- 현상수배 발동 확인
- 격차를 7% 이하로 낮춤
- 해제 타이밍 확인

완료 기준:

- 선두 팀이 억울하지 않고, 추격 팀이 보상을 노릴 이유가 있어야 합니다.

## P2. MatchStatsService 이벤트 레벨 재검토

문제:

- `NORMAL`, `LOW` 이벤트는 상한이 있어 오래 플레이하면 일부가 제거됩니다.
- 밸런스 분석에 필요한 이벤트가 `NORMAL`에 있으면 누락될 수 있습니다.

권장 작업:

- 현상수배 보상, 상점 구매, 코인 획득은 `HIGH` 유지
- 코인 드랍은 표본 분석에 중요하므로 장기전에서 샘플링 또는 별도 summary 집계 검토

## P3. `Mayuela.java` Composition Root 정리

문제:

- 모든 서비스, 커맨드, 리스너 생성이 `Mayuela.java`에 모여 있습니다.

현재 판단:

- 작은 플러그인에서는 허용 가능합니다.
- 다만 서비스가 더 늘면 생성 순서와 생성자 인자가 부담됩니다.

후속 방향:

- `MayuelaContext`
- `ServiceRegistry`
- `CommandRegistrar`
- `ListenerRegistrar`

정도로만 나누고, 과한 DI 프레임워크는 도입하지 않습니다.
