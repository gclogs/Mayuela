# 방어팀 가이드

이 문서는 레드팀 검토에서 드러난 위험을 막기 위한 개발/운영 방어 전략입니다.

## 방어팀 구성

| 역할 | 책임 |
| --- | --- |
| 아키텍처 방어 | 책임 분리, 상태 소유권, 의존성 방향 관리 |
| TPS 방어 | Paper main thread 부하, 스케줄러 주기, 엔티티 수 관리 |
| 경제 방어 | 코인 수급/소비/보상 밸런스 검증 |
| 전투 방어 | 스폰킬, CC 연계, 무적/저항 상태 검증 |
| 데이터 방어 | 재접속, 종료, reload, 통계 저장 일관성 검증 |
| 운영 방어 | 명령어 안내, 모니터링, 문서 최신성 유지 |

## 핵심 불변조건

새 기능을 추가하거나 수정할 때 다음 조건이 깨지면 안 됩니다.

### 게임 세션

- `WAITING`에서는 게임 아이템을 설치/사용/드롭할 수 없어야 합니다.
- `READY`에서는 준비 아이템을 받지만 제단 설치와 아이템 드롭은 막아야 합니다.
- `PLAYING`에서만 제단 설치, 코인 드랍, 상점 구매, 활성화율 증가가 의미를 가집니다.
- `ENDING` 또는 강제 종료 시 DisplayEntity, BossBar, 코인 엔티티, 스케줄러가 정리되어야 합니다.

### 팀

- 팀전은 짝수 인원이어야 합니다.
- 팀전은 최소 4명, 권장 최대 10명입니다.
- 한 팀은 최대 2명입니다.
- 팀 색상은 스코어보드, 갑옷, 제단 아이템, DisplayEntity, 통계에서 같은 기준을 사용해야 합니다.

### 제단

- 제단은 등록된 신호기 위치에서만 유효합니다.
- 신호기 GUI는 게임 중 열리지 않아야 합니다.
- 제단 블록은 서버가 강제로 설치합니다.
- 제단 블록 파괴 시 아이템 드랍이 나오면 안 됩니다.
- 일반 블록 파괴는 게임 준비/진행 중 막아야 합니다.
- 제단 상태가 바뀌면 스코어보드, 아이템 lore, TextDisplay가 함께 갱신되어야 합니다.

### 코인

- 추적 중인 필드 코인만 획득 처리합니다.
- 코인은 버릴 수 없어야 합니다.
- 상점 구매는 실제 인벤토리의 Mayuela 코인만 차감해야 합니다.
- 필드 코인 만료/획득/게임 종료 시 TextDisplay도 제거되어야 합니다.
- 코인 설정 변경은 통계 파일에 기록되어야 분석이 가능합니다.

### 현상수배

- 현상수배 대상은 최대 1팀입니다.
- 현상수배 대상은 현재 1등 팀만 가능합니다.
- 1등이라고 해서 무조건 현상수배가 되면 안 됩니다.
- 리드 격차가 발동 기준 이상이고 워밍업/최소 진행률/쿨다운 조건을 만족해야 합니다.
- 일반 플레이어 UI에는 리드 격차를 노출하지 않습니다.
- 리드 격차는 `/game 모니터링`에서만 확인합니다.
- 처치 보상은 설정값 `bounty.reward-coins`를 사용합니다.
- 같은 현상수배 플레이어에 대한 보상은 현상수배 상태 1회당 1번만 지급합니다.

## TPS 방어 원칙

Paper 서버는 main thread에서 게임 로직과 월드 조작이 돌아갑니다. Mayuela는 작은 미니게임이지만 DisplayEntity와 스케줄러가 많아질 수 있으므로 다음 원칙을 지킵니다.

### 금지에 가까운 패턴

- 매 tick 전체 월드 엔티티 스캔
- 매 tick 모든 블록 범위 탐색
- 매 tick 모든 플레이어 스코어보드 재생성
- 매 tick 모든 TextDisplay 텍스트 재설정
- 이벤트마다 YAML 저장
- DisplayEntity를 반복 생성/삭제하는 방식의 애니메이션

### 허용되는 패턴

- 최대 10명 플레이어의 머리 위 ItemDisplay teleport
- 코인 최대 40개 기준 1초 단위 TextDisplay 갱신
- 제단 활성화율 tick 주기에서 스코어보드 갱신
- 이벤트 발생 시 메모리 통계 버퍼에 기록
- 매치 종료 시 YAML 저장

### 방어 기준

| 항목 | 권장 한계 |
| --- | --- |
| 플레이어 | 10명 이하 |
| 필드 코인 | 40개 이하 |
| 코인 TextDisplay | 필드 코인 수와 동일 |
| 플레이어 ItemDisplay | 플레이어 수와 동일 |
| 현상수배 TextDisplay | 현상수배 팀 온라인 인원 이하 |
| 제단 TextDisplay | 등록 제단 수와 동일 |

## SOLID 적용 기준

이 프로젝트는 1인 개발이므로 과한 추상화는 피합니다. 하지만 다음 원칙은 유지해야 합니다.

### SRP: 단일 책임

- `CoinService`는 코인 생성/드랍/획득/만료를 담당합니다.
- `ShopService`는 구매와 코인 차감을 담당합니다.
- `AltarService`는 제단과 현상수배 판정을 담당합니다.
- `DisplayService`는 DisplayEntity 생성/갱신/삭제를 담당합니다.

위반 징후:

- 한 서비스가 명령어 파싱, YAML 저장, 엔티티 조작, 스코어보드까지 모두 직접 처리하기 시작합니다.

### OCP: 확장에는 열고 수정에는 닫기

아이템 추가 시 권장 흐름:

1. `ConfigRepository`에 가격/시간/fallback 기본값 추가
2. `ShopService.ShopItem`에 항목 추가
3. `model.yml` 기본값 추가
4. `ShopItemListener`에 사용 효과 추가
5. `MatchStatsService`에 사용/구매 통계 확인
6. 문서 업데이트

### DIP: 의존성 역전

현재는 인터페이스보다 구체 서비스 직접 주입이 많습니다. 작은 프로젝트라 허용하지만, 다음 시점에는 인터페이스 분리를 고려합니다.

- ItemsAdder 연동 코드가 3개 이상 서비스에서 중복될 때
- 통계 저장 방식이 YAML 외 DB/CSV로 늘어날 때
- 테스트에서 Bukkit API를 직접 mocking하기 어려울 때

## 방어 구현 패턴

### 설정을 추가할 때

반드시 함께 수정:

- `ConfigRepository.load()` 기본값
- getter
- 운영자 문서
- 매치 통계 설정 저장
- 필요하면 `/game 모니터링`

### PDC 태그를 추가할 때

반드시 함께 수정:

- 생성 서비스
- 판별 서비스
- `PdcMonitorService`로 읽히는지 확인
- 운영자 명령어 가이드

PDC 이름 규칙:

```text
mayuela:<domain>_<purpose>
```

예:

- `mayuela:coin`
- `mayuela:coin_itemsadder_id`
- `mayuela:shop_item`
- `mayuela:shop_itemsadder_id`
- `mayuela:color_block`
- `mayuela:flag_itemsadder_id`

### DisplayEntity를 추가할 때

반드시 함께 수정:

- 생성 위치
- 갱신 주기
- 제거 시점
- 게임 종료 정리
- 재접속/리스폰 복구 여부
- TPS 영향

제거 시점 체크:

- 획득
- 파괴
- 만료
- 게임 종료
- 플레이어 퇴장
- 플러그인 disable

### 스케줄러를 추가할 때

반드시 함께 수정:

- 시작 시점
- 중지 시점
- `forceStop()`
- `onDisable()`
- 중복 시작 방지
- 작업 주기와 최대 처리량

## 운영 방어

운영 중 반드시 확인할 명령:

```text
/game 모니터링
/game pdc
/game pdc 인벤토리
/game reload
```

운영자가 봐야 하는 것:

- 현재 페이즈
- 등록 제단 수
- 게임 스폰 등록 여부
- 필드 코인 수
- 코인 룰
- 코인 자동 제거 시간
- 플레이어별 코인 앵커/획득량
- 현상수배 상태
- 현상수배 발동 가능 여부
- 현상수배 리드 격차

## 배포 전 방어 체크

- `compileJava` 성공
- `/game 시작` 실패 사유가 구체적으로 출력됨
- 4명 팀전 시작 가능
- 1명/2명 개인전 또는 서비스 단위 테스트로 최소 흐름 확인
- 게임 종료 시 모든 DisplayEntity 제거
- 게임 종료 시 인벤토리/갑옷 상태 정상
- 재접속 시 보스바/스코어보드/버프/현상수배 표시 복구
- 코인 드랍 TextDisplay가 만료/획득 시 제거
- 현상수배 보상 1회 제한 동작

## 방어팀 결론

Mayuela의 핵심 방어선은 다음입니다.

1. 상태 소유권을 흐리지 않는다.
2. 설정값을 추가하면 통계와 모니터링도 같이 추가한다.
3. DisplayEntity는 항상 제거 경로를 먼저 설계한다.
4. 코인 경제는 획득/소비/보유를 분리해서 본다.
5. 현상수배는 밸런스 장치이므로 일반 UI에는 과한 정보를 노출하지 않는다.
